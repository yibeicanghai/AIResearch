## 1. 核心澄清：序列长度的常见误解

### 1.1 用户的合理质疑

> "原始像素经过 ViT/VAE 压缩后不是应该拿到更少的 token 吗，为何说像素空间直接处理路线序列会更短？"

这个直觉**部分正确**：VAE 确实通过空间压缩减少了 token 数。但关键在于比较的对象：

### 1.2 两个不同的比较维度

| 比较维度 | 结论 |
|---------|------|
| **单流 vs 单流**：像素 patch vs VAE latent | VAE latent **更少**（因为 VAE 做了空间压缩） |
| **双流 vs 单流**：ViT+VAE 双流 vs 像素单流 | 像素单流**更少**（因为去掉了 ViT 流） |

PixelUMM 所说的"序列更短"是**第二种比较**——针对 BAGEL 这类需要**同时维护 ViT 和 VAE 两套视觉 token 流**的模型。

### 1.3 为什么 BAGEL 需要双流？

- **ViT token**：提供语义特征，服务于理解（VQA、描述、识别）
- **VAE token**：提供重建特征，服务于生成和编辑（需要保住细粒度细节）
- **两者不可相互替代**：ViT 特征丢了重建细节，VAE 特征丢了语义信息
- 因此在编辑/参考类任务中，**同一张条件图像必须同时编入 ViT 和 VAE 两份 token**

### 1.4 像素空间为何只需单流？

- 原始像素**同时包含语义和细节信息**
- 理解任务：干净像素通过 understanding 投影进入
- 生成任务：加噪像素通过 generation 投影进入
- **同一份像素 token 服务两种任务**，无需维护两套编码器

## 2. 序列长度量化对比

### 2.1 基础参数设定

以下基于论文中的实际配置：

| 参数 | 取值 | 来源 |
|------|------|------|
| 图像分辨率 | 512×512 | PixelUMM Joint Stage 2 生成分辨率 |
| ViT patch 大小 | 16×16 | BAGEL / 主流 ViT 配置 |
| 像素 patch 大小 | 16×16 | PixelUMM 默认配置 (p=16) |
| VAE 空间压缩率 | 8×（Wan2.2 VAE 为 16×，配合 2×2 latent patch → 32× 有效） | PixelUMM F4 实验 |
| 视频帧数 | 96 帧 / 448×448 每帧 | PixelUMM 默认视频配置 |
| 视频 tubelet | 4 帧 × 16×16 | PixelUMM 默认 (τ=4, p=16) |

单张 512×512 图像的 token 数：

| 编码方式 | 计算过程 | token 数 |
|---------|---------|---------|
| ViT (16×16 patch) | (512/16)² = 32×32 | **1,024** |
| VAE (8× 压缩，无额外 patch) | (512/8)² = 64×64 | **4,096** |
| VAE (16× 压缩 + 2×2 latent patch = 32× 有效) | (512/32)² = 16×16 | **256** |
| 像素 (16×16 patch) | (512/16)² = 32×32 | **1,024** |
| 像素 (32×32 patch) | (512/32)² = 16×16 | **256** |

### 2.2 场景一：纯理解任务（单张图像 VQA）

| 组件 | BAGEL (ViT) | PixelUMM (像素) |
|------|------------|----------------|
| 条件图像 token | ViT: 1,024 | 像素: 1,024 |
| 文本 token | ~50 | ~50 |
| **总序列长度** | **~1,074** | **~1,074** |

**结论：纯理解任务，两者序列长度相当**。PixelUMM 无优势也无劣势。

### 2.3 场景二：纯生成任务（文生图，512×512）

| 组件 | BAGEL (VAE) | PixelUMM (像素 16×16) | PixelUMM (像素 32×32) |
|------|------------|----------------------|----------------------|
| 生成目标 token | VAE: 256 (32× 有效) | 像素: 1,024 | 像素: 256 |
| 文本 prompt token | ~50 | ~50 | ~50 |
| **总序列长度** | **~306** | **~1,074** | **~306** |

**结论：纯生成任务，VAE 压缩的 token 更少**。除非用 32×32 patch（但 PixelUMM F1 实验显示 32×32 patch 质量下降），否则像素空间在纯生成时序列更长。这是像素空间路线的**真实代价**。

### 2.4 场景三：图像编辑任务（1 张参考图 + 1 张生成目标，512×512）

这是 PixelUMM 声称序列更短的**核心场景**。

| 组件 | BAGEL (ViT + VAE 双流) | PixelUMM (像素单流, 16×16) |
|------|----------------------|--------------------------|
| 参考图 ViT token | 1,024 | 0 (无 ViT) |
| 参考图 VAE token | 256 (32× 有效) | 0 (无 VAE) |
| 参考图像素 token | 0 | 1,024 |
| **参考图小计** | **1,280** | **1,024** |
| 生成目标 VAE/像素 token | 256 | 1,024 |
| 文本指令 token | ~30 | ~30 |
| **总序列长度** | **~1,566** | **~2,078** |

**等等——这里 PixelUMM 反而更长！** 因为生成目标的像素 token (1,024) 远多于 VAE latent token (256)。

那 PixelUMM 到底什么时候更短？关键在**多条件图像场景**：

### 2.5 场景四：多图编辑对话（3 张参考图 + 1 张生成目标，512×512）

| 组件 | BAGEL (ViT + VAE 双流) | PixelUMM (像素单流, 16×16) |
|------|----------------------|--------------------------|
| 3 张参考图 ViT token | 3 × 1,024 = 3,072 | 0 |
| 3 张参考图 VAE token | 3 × 256 = 768 | 0 |
| 3 张参考图像素 token | 0 | 3 × 1,024 = 3,072 |
| **参考图小计** | **3,840** | **3,072** |
| 生成目标 token | 256 | 1,024 |
| 文本 token | ~100 | ~100 |
| **总序列长度** | **~4,196** | **~4,196** |

**仍然相当！** 因为生成目标的像素 token 多出的部分抵消了参考图省下的 ViT token。

### 2.6 场景五：多轮多图对话（关键场景，5 轮对话，每轮 1 张图，512×512）

这是 PixelUMM 论文强调的场景："visual tokens accumulate across images, video frames, and dialogue turns"。

| 组件 | BAGEL (ViT + VAE 双流) | PixelUMM (像素单流, 16×16) |
|------|----------------------|--------------------------|
| 5 张历史图 ViT token | 5 × 1,024 = 5,120 | 0 |
| 5 张历史图 VAE token | 5 × 256 = 1,280 | 0 |
| 5 张历史图像素 token | 0 | 5 × 1,024 = 5,120 |
| **历史图小计** | **6,400** | **5,120** |
| 当前轮生成目标 token | 256 | 1,024 |
| 文本 token (5 轮) | ~250 | ~250 |
| **总序列长度** | **~6,906** | **~6,394** |

PixelUMM 略短（约 7.4%），但优势不大。

### 2.7 场景六：多轮多图对话，VAE 压缩率较低时（编辑需要保细节）

关键洞察：**编辑任务需要 VAE 保留细节，不能用太激进的压缩**。如果 VAE 只用 8× 压缩（而非 32× 有效）：

| 组件 | BAGEL (ViT + VAE 8× 双流) | PixelUMM (像素单流, 16×16) |
|------|--------------------------|--------------------------|
| 5 张历史图 ViT token | 5 × 1,024 = 5,120 | 0 |
| 5 张历史图 VAE token (8×) | 5 × 4,096 = 20,480 | 0 |
| 5 张历史图像素 token | 0 | 5 × 1,024 = 5,120 |
| **历史图小计** | **25,600** | **5,120** |
| 当前轮生成目标 token | 4,096 | 1,024 |
| 文本 token | ~250 | ~250 |
| **总序列长度** | **~29,946** | **~6,394** |

**PixelUMM 仅为 BAGEL 的 21%（5× 压缩）！**

这才是 PixelUMM 所说的"approximately doubles"的真实含义：**当 VAE 需要保留足够细节用于编辑时（不能压缩太狠），VAE token 数量与 ViT 相当甚至更多，双流 = 2× 或更多倍单流。**

### 2.8 场景七：视频理解（96 帧，448×448）

| 组件 | BAGEL (ViT 逐帧) | PixelUMM (时空 tubelet 4×16×16) |
|------|-----------------|-------------------------------|
| 每帧 ViT token (16×16) | (448/16)² = 784 | — |
| 96 帧 ViT token 总数 | 96 × 784 = **75,264** | — |
| tubelet 数 (4帧×16×16) | — | (96/4) × (448/16)² = 24 × 784 = **18,816** |
| **总视觉 token** | **75,264** | **18,816** |

**PixelUMM 仅为 BAGEL 的 25%（4× 压缩）！** 视频场景下，tubelet 的时空联合压缩显著优于逐帧 ViT 编码。

### 2.9 序列长度对比总结

| 场景 | BAGEL vs PixelUMM | PixelUMM 优势 |
|------|-------------------|-------------|
| 纯理解（单图 VQA） | ~相当 | 无 |
| 纯生成（文生图） | VAE 更少 | **劣势**（像素 token 更多） |
| 单图编辑 | ~相当 | 微弱 |
| 多图编辑（VAE 高压缩） | ~相当 | 微弱 |
| 多图编辑（VAE 低压缩保细节） | PixelUMM 远短 | **显著（2-5×）** |
| 多轮多图对话（VAE 低压缩） | PixelUMM 远短 | **显著（2-5×）** |
| 视频理解 | PixelUMM 远短 | **显著（4×）** |

**核心结论**：

1. **PixelUMM 的序列优势不是绝对的**——在纯生成场景，像素 token 确实比 VAE latent 多
2. **优势集中在"条件图像"（参考图/历史图）的处理上**——BAGEL 需要双流（ViT+VAE），PixelUMM 只需单流
3. **优势在以下条件下放大**：
   - 多图/多轮对话（token 累积）
   - VAE 压缩率不能太高（编辑需要保细节）
   - 视频理解（tubelet 时空压缩优于逐帧 ViT）
4. **PixelUMM 论文原文的精确表述**："approximately doubles the visual context **compared with a single visual stream of similar token resolution**"——即"在单流 token 分辨率相近时，双流使其翻倍"

## 3. 传统 ViT/VAE 双编码器接口的问题

### 3.1 接口架构

当前主流统一多模态模型（如 BAGEL）处理视觉信息时采用**双流接口**：

| 组件 | 角色 | 提供的特征类型 |
|------|------|-------------|
| **ViT** (Vision Transformer) | 服务于**理解**任务 (VQA、描述、识别) | 语义特征 (高层抽象) |
| **VAE** (Variational Autoencoder) | 服务于**生成**任务 (文生图、编辑) | 重建特征 (低层细节) |

同一张图像被两套独立的编码器编码两次，产生两份不同性质的视觉 token。

### 3.2 问题一：视觉上下文翻倍（PixelUMM）

- 每张条件图像同时产生 ViT token 和 VAE token，**视觉上下文近似翻倍**
- 在多图、多轮对话、长视频场景中，视觉 token 跨图像、跨帧、跨轮次累积
- **attention 与 KV-cache 成本随上下文增长**（attention 是 O(N²)）
- 这种冗余在长上下文处理中"尤其不可接受"

### 3.3 问题二：与既有 VLM 预训练范式不兼容（PixelUMM）

- 主流视觉-语言预训练 (VLM) 使用**单一视觉流**
- 引入 VAE token 需要对现有数据管线和训练配方做**大幅重构**
- 在预训练阶段引入双流改动，使"统一"变得**不切实际**

### 3.4 问题三：VAE 有损重建限制生成质量上限（PixelDiT）

- VAE 采用有损压缩，**移除高频细节和精细结构**
- 即便扩散模型本身很强，**样本保真度仍被 VAE 重建能力所界定**
- PixelDiT 用 FlowEdit 编辑实验直观展示：FLUX 和 SD3 的 VAE 在编码阶段就已将图像中的小字扭曲，误差在 latent 扩散中进一步累积

### 3.5 问题四：VAE 重建目标与生成目标不对齐（PixelDiT）

- VAE 训练目标是**重建**，下游任务是**生成**——两者只是部分对齐
- 这种不对齐在 latent 空间引入**分布偏移**（如纹理平滑、颜色偏移）
- 扩散模型必须去补偿这些偏移，增加学习负担

### 3.6 问题五：VAE 带来额外开销（PixelDiT）

- **训练开销**：预训练或协同训练大型 autoencoder 增加数据和算力成本
- **推理开销**：采样时需要额外解码，相比像素空间模型增加延迟
- **训练流程**：两阶段管线（先训 VAE，再训扩散模型），无法端到端联合优化

### 3.7 问题六：latent space 只是"隐藏"了预测噪声的困难（JiT）

- 在 latent 空间预测噪声可行，是因为 latent 已被压缩到低维
- 但一旦回到像素等高维空间，**预测噪声 (ε) 或带噪量 (v) 会灾难性失败**
- JiT 的核心洞察：自然数据位于低维流形上，但**噪声不在此流形上**
  - 预测噪声需要网络保留全部高维噪声信息（高容量需求）
  - 预测干净数据只需保留低维流形信息（低容量即可）
- VAE 的压缩只是**把问题藏起来**，并未真正解决

### 3.8 问题七：对预训练 latent 空间的依赖使模型无法"自洽"（JiT）

- 扩散模型严重依赖一个外部预训练的 latent 空间，**无法独立工作**
- JiT 追求 **self-contained** 的 "Diffusion + Transformer" 范式
- 希望推广到蛋白质、分子、天气等 **tokenizer 难以设计** 的领域

## 4. 三篇论文的出发点详解

### 4.1 JiT (MIT, Tianhong Li & Kaiming He, arXiv:2511.13720)

**核心论点**：预测目标 (x vs ε/v) 才是关键，不是架构

**关键洞察**：
- 原始扩散模型的核心思想是"从被损坏的版本预测干净图像"
- 但 DDPM 发现 ε-prediction 效果更好，flow-based 用 v-prediction
- 今天的扩散模型预测的是**噪声或带噪量**，而非干净图像本身
- 在流形假设下，干净数据 on-manifold（低维），噪声 off-manifold（高维）
- 预测干净数据与预测噪声**根本不同**

**对 VAE 的批评**：
- latent space 只是"隐藏"了预测噪声的困难，而非"解决"
- 对预训练 latent 空间的严重依赖使扩散模型无法"自洽"
- 既有像素空间方法（SiD2、PixelFlow、PixNerd）的复杂设计（密集卷积、小 patch、长 skip）可能源于"预测高维带噪量"的需求

**方案**：x-prediction + 标准 ViT + 大 patch (16×16, 32×32) 原始像素，无 tokenizer、无预训练、无辅助损失

### 4.2 PixelDiT (NVIDIA & University of Rochester, arXiv:2511.20645, CVPR 2026)

**核心论点**：架构（pixel modeling 机制）才是关键

**对 LDM 的批评**（两条结构性限制）：
1. 扩散被绑定到单独预训练的 autoencoder，重建目标与生成目标部分不对齐
2. Autoencoder 引入有损重建，移除高频细节，限制样本保真度上限

**"Why revisit pixel space?" 的四点理由**：
1. 保真度受限于 autoencoder
2. 预训练/协同训练 autoencoder 增加开销
3. 目标不对齐导致分布偏移（纹理平滑、颜色偏移）
4. 采样时解码延迟

**识别的核心挑战**："pixel modeling"——缺乏高效的逐像素建模机制
- 激进 patchify → attention 可负担但弱化逐像素建模
- 近像素粒度 → 保细节但二次复杂度成本高
- 级联管线 → 降低成本但引入额外阶段与累积误差

**方案**：双层级架构（patch-level DiT 全局语义 + pixel-level DiT 纹理细节）+ pixel-wise AdaLN + pixel token compaction

### 4.3 PixelUMM (NVIDIA & University of Waterloo, arXiv:2609.38597)

**核心论点**：把像素空间范式从图像扩展到图像+视频的统一多模态

**对 BAGEL 双流接口的批评**：
1. 每张条件图像用 ViT + VAE 双重编码，视觉上下文翻倍
2. 与主流 VLM 单流预训练范式不兼容
3. 双流接口在预训练阶段使统一"不切实际"

**技术挑战**：视频理解和生成采用不同的时间表示
- 视频生成常用因果 3D VAE（首帧单独编码）
- 视频理解常用图像编码器逐帧处理
- 两种惯例不自然共享接口

**方案**：
- 图像 = 空间 patch (16×16)，视频 = 时空 tubelet (4×16×16)
- 单层线性投影连接像素和骨干网络
- Mixture-of-Transformers：共享 self-attention + 理解/生成各自专家参数
- 联合自回归文本预测 + 像素空间 flow matching

## 5. 像素空间建模如何解决这些问题

| 问题 | 像素空间方案的应对 |
|------|------------------|
| 视觉上下文翻倍（条件图） | 单一像素流替代 ViT+VAE 双流，条件图 token 减半 |
| 与 VLM 预训练不兼容 | 单一视觉流天然兼容主流 VLM 管线 |
| VAE 有损重建 | 无 VAE，直接操作原始像素，无信息丢失 |
| 重建与生成目标不对齐 | 端到端联合训练，无目标错位 |
| VAE 额外开销 | 单阶段训练，无解码步骤 |
| latent 隐藏预测噪声的困难 | JiT: 改为预测干净图像 x（而非 ε/v） |
| 模型不自洽 | 无外部依赖，self-contained |

## 6. 通俗解释

### 6.1 用"翻译"来理解

想象你要建一个**能看图、能说话、能画图**的 AI 助手。

**传统做法**相当于给这个助手配了两个"翻译"：
- 一个翻译 (ViT) 负责**把图片翻译成"语义摘要"**，让助手能"看懂"图片内容
- 另一个翻译 (VAE) 负责**把图片压缩成"重建草图"**，让助手能"画出来"

同一张图要让两个翻译各处理一遍，助手同时拿到两份材料。问题是：

1. **材料太多，桌子放不下**——多图、多轮对话时，材料越堆越多，助手处理不过来（上下文翻倍）
2. **两套翻译流程不统一**——其他助手团队都只用一套翻译流程，你这个要用两套，对接很麻烦（与 VLM 预训练不兼容）
3. **重建翻译会丢细节**——VAE 在压缩图片时会丢掉精细纹理，文字、细节都糊了（有损重建）
4. **重建翻译的目标不对**——VAE 训练时只求"能还原原图"，但助手真正需要的是"能生成新图"（目标不对齐）
5. **养两个翻译成本高**——要先训练好 VAE 再训练扩散模型，推理时还要额外解码（额外开销）

**像素空间做法**相当于：**辞掉两个翻译，让助手直接看原图像素**。

### 6.2 序列长度的通俗解释

> "VAE 压缩后不是 token 更少吗？为什么说像素空间序列更短？"

**关键区分**：比较的是"双流"还是"单流"。

- 如果只雇一个翻译（VAE），他确实能把 1000 页材料压缩成 250 页（VAE 压缩）
- 但 BAGEL 雇了**两个翻译**（ViT + VAE），一个产出 1024 页，另一个产出 256 页，总共 1280 页
- PixelUMM 只用一份原始像素，1024 页

**在条件图（参考图/历史图）上**：BAGEL 1280 页 > PixelUMM 1024 页 → PixelUMM 更短

**在生成目标上**：BAGEL 256 页（VAE 压缩） < PixelUMM 1024 页（原始像素）→ BAGEL 更短

**净效果取决于场景**：
- 纯生成：BAGEL 更短（VAE 压缩优势）
- 多图编辑/多轮对话：PixelUMM 更短（去掉 ViT 流的优势累积）
- 视频理解：PixelUMM 更短（tubelet 时空压缩优于逐帧 ViT）

### 6.3 JiT 的洞察（通俗版）

难的不是像素空间，而是"预测目标选错了"。

过去让网络**预测噪声**——噪声充满整个高维空间，网络必须有足够容量才能记住所有噪声。这就像让助手记住图片上每一粒灰尘的位置。

但如果让网络**直接预测干净图像**——自然图片真正有用的信息是低维的（物体形状、颜色、结构），网络只需抓住关键信息，把噪声滤掉即可。

### 6.4 PixelDiT 的洞察（通俗版）

难的是"像素建模机制"，而非像素空间本身。

要么用大 patch（省算力但丢细节），要么用小 patch（保细节但算力爆炸）。PixelDiT 的解法是**双层级架构**：粗粒度层负责全局语义（像看缩略图），细粒度层负责纹理细节（像拿放大镜看局部）。

## 7. 总结

### 7.1 去掉 ViT/VAE 的七大原因

| # | 原因 | 提出论文 |
|---|------|---------|
| 1 | 条件图像双流编码导致视觉上下文翻倍 | PixelUMM |
| 2 | 双流接口与主流 VLM 单流预训练范式不兼容 | PixelUMM |
| 3 | VAE 有损重建限制生成质量上限 | PixelDiT |
| 4 | VAE 重建目标与生成目标不对齐 | PixelDiT |
| 5 | VAE 带来额外训练与推理开销 | PixelDiT |
| 6 | latent space 只是隐藏而非解决预测噪声的困难 | JiT |
| 7 | 对预训练 latent 空间的依赖使模型无法自洽 | JiT |

### 7.2 序列长度的精确理解

| 场景 | 像素空间 vs VAE 双流 | 原因 |
|------|---------------------|------|
| 纯理解（单图） | 相当 | 单流 vs 单流，token 数相近 |
| 纯生成 | 像素更长 | VAE 压缩后 token 更少 |
| 单图编辑 | 相当 | 生成目标多出的 token 抵消了条件图省下的 |
| 多图编辑（VAE 低压缩保细节） | **像素更短（2-5×）** | 去掉 ViT 流 + VAE 不能压缩太狠 |
| 多轮多图对话 | **像素更短（2-5×）** | 条件图累积，双流劣势放大 |
| 视频理解 | **像素更短（4×）** | tubelet 时空压缩优于逐帧 ViT |

### 7.3 三篇论文的方案对比

| 维度 | JiT (MIT) | PixelDiT (NVIDIA) | PixelUMM (NVIDIA) |
|------|-----------|-------------------|-------------------|
| 核心论点 | 预测目标才是关键 | 架构（pixel modeling）才是关键 | 扩展到图像+视频统一多模态 |
| 对 VAE 的批评 | 使模型不自洽，隐藏困难 | 有损重建、目标不对齐、额外开销 | 双流翻倍上下文、不兼容 VLM |
| 解决思路 | 改预测目标为 x-prediction | 设计双层级 Transformer | 单层线性投影 + MoT 架构 |
| 哲学定位 | self-contained，可推广到非视觉 | 单阶段端到端像素扩散 | encoder-free 统一多模态 |

### 7.4 一句话总结

> **ViT/VAE 双编码器接口在条件图像处理上导致视觉上下文翻倍、与主流预训练范式不兼容、VAE 有损重建限制质量上限、且只是"隐藏"而非"解决"高维预测噪声的困难。像素空间建模通过单一像素流同时服务理解和生成，在多图/多轮/视频场景下显著缩短序列；代价是纯生成目标的序列可能更长（无 VAE 压缩），需通过模型规模扩展（JiT 的 x-prediction、PixelDiT 的双层级架构、PixelUMM 的 MoT）来补偿。**
